## 10-2. オーケストレーションの 3 パターン（スライド36, 37）

### ① Hub-and-Spoke（並行）

```
             メイン
           ／  ｜  ＼
       探索  計画  実装  テスト
       （同時に委譲、報告は親のみ）
```

- **特徴**: 1 つの親が複数の子に並行委譲
- **メリット**: 速い、互いに独立、スケールしやすい
- **デメリット**: タスク間の依存に弱い、結果の統合が必要、親がボトルネック
- **向く場面**: リファクタリング / テスト並行実行 / 独立した調査
- **実装**: サブエージェント + `/batch`

### ② リレー / チェーン（順次）

```
仕様生成 → テスト作成 → 実装 → レビュー
（前の出力が次の入力）
```

- **特徴**: 前の出力が次の入力
- **メリット**: 品質が段階的に積上、各ステップで検証可、順序が明確
- **デメリット**: 直列なので遅い、前段の失敗が全体に波及
- **向く場面**: SDD サイクル / CI/CD パイプライン / ドキュメント生成
- **実装**: Skills のチェーン実行

### ③ Agent Teams（協調）

```
        Lead（計画）
     ／    ｜    ＼
    FE    BE    Test
    ← 相互メッセージ可能 →
    （共有タスクリスト）
```

- **特徴**: Lead が計画、メンバーが自律実行、相互調整可能
- **メリット**: 相互調整が可能、大規模タスク向き、柔軟な役割分担
- **デメリット**: 設計が複雑、コストが高い、デバッグが難しい
- **向く場面**: フルスタック開発 / FE+BE+DB 連携 / 設計レビュー
- **実装**: Agent Teams（`claude --team`）

### パターン選択の判断フロー

```
タスクは独立？ ──→ Yes ──→ Hub-and-Spoke
    ↓
    No
    ↓
順序に依存？ ──→ Yes ──→ リレー / チェーン
    ↓
    No
    ↓
相互調整が必要？ ──→ Yes ──→ Agent Teams
```

> **迷ったらまず Hub-and-Spoke。** 最もシンプルで、多くのケースで十分。複雑さは必要になってから足す。

### Tier 構造

```
Tier 1: 組込み（サブエージェント / Teams）
  ↓
Tier 2: 外部オーケストレータ
  ↓
Tier 3: クラウド（Managed Agents・非同期 PR）
```

## 10-3. 公式：Anthropic "Building Effective Agents"（スライド49）

> **出典**: Anthropic 公式ブログ "Building Effective Agents"
> **原則**: **複雑さは成果を改善する場合にのみ追加する。**
> 最も洗練されたシステムではなく、**正しいシステム** を作る。まず単一 LLM → 不十分なら段階的に複雑にする。

### 5 つのパターン

| # | パターン | 説明 | 活用例 | Claude Code での対応 |
|---|---|---|---|---|
| 1 | **Prompt Chaining** | 前の出力が次の入力 | 仕様→設計→実装→レビュー | Skills のチェーン実行 |
| 2 | **Routing** | 入力を分類し専門へ振分 | 簡単→Haiku / 難→Opus | Agent 定義の `model` 指定 |
| 3 | **Parallelization** | 独立タスクを同時実行 | テスト+Lint+型チェック | `/batch` + fork 型サブエージェント |
| 4 | **Orchestrator-Workers** | 中央が動的に分割・委譲 | 複数ファイル変更・検索 | Agent Teams |
| 5 | **Evaluator-Optimizer** | 生成→評価→改善ループ | 翻訳・コード品質向上 | PGE ループ（体験④） |

### 3 原則

1. **シンプルに保つ**
2. **計画過程を透明にする**
3. **ツールの IF を丁寧に設計する**

## 10-4. マルチエージェント実装比較（スライド50）

| | Subagent | Agent Teams | Managed Agents（API） |
|---|---|---|---|
| **構造** | メインセッション内で fork | 独立プロセス / tmux ペインで起動 | Anthropic クラウド上コンテナで実行 |
| **通信** | 親に結果を返すのみ（一方向） | ファイルベースの**メールボックス**で相互メッセージ | SSE ストリーム / Webhook |
| **コンテキスト** | 親と共有（キャッシュヒット） | 完全に独立（各自のウィンドウ） | 独立コンテナ（サンドボックス） |
| **コスト** | 低い（fork でキャッシュ共有） | 高い（各自フルコンテキスト） | $0.08/時間 + トークン費用 |
| **向く場面** | 短い調査・検証、コンテキスト節約 | FE/BE/Test 並行開発、クロスレイヤー調整 | 長時間の自律タスク、CI/CD・PR レビュー |

### 選び方の判断フロー

```
エージェント同士が会話する必要がある？
  No → Subagent（最もシンプル。まずここから）
  Yes → Agent Teams（チームメイト間で直接メッセージ可能）

人間が離席しても動き続けてほしい？
  Yes → Managed Agents（クラウドで自律実行）
```

> **コスト最適化**: Haiku でサブタスク + Opus で複雑な推論 = モデルミックスで 60–70% コスト削減可能。

## 10-5. ベストプラクティス 3 柱（スライド51–53）

### 柱① コンテキスト管理（スライド51）

| 原則 | 実践 |
|---|---|
| 1 タスク 1 セッション | タスクが変わったら `/clear` |
| 70% で `/compact` | 自動任せにしない |
| 修正 2 回で `/clear` | コンテキスト汚染のサイン |
| 調査はサブエージェントへ | メインを汚さない |

**CLAUDE.md のコツ**: 50–100 行 / 詳細はポインタ / `/init` で生成→育てる / ルールは Rules に分離

> **CLAUDE.md の指示は約 70% の確率で守られる。100% 必要なルールは Hooks で強制する。**

### 柱② 計画とプロンプト（スライド52）

> **80% 正解率 × 20 判断ポイント = 全問正解率 1%。** 計画がこの確率を劇的に引き上げる。
> Anthropic の内部テスト：計画なしの成功率は約 33%。計画ありで大幅に改善。

**Plan Mode の使い方**:
- `Shift+Tab` で切替
- 3 ステップ以上のタスクは必ず Plan Mode で開始
- 構造化して確認 → 承認してから実行

**プロンプトのコツ**: ファイルを直接参照 / URL・画像を貼る / 具体的に指示 / 挑戦させる

### 柱③ スケーリングとチーム運用（スライド53）

**並行セッションで品質を上げる**:
- **Writer / Reviewer 分離** — 1 つの Claude が書いたコードを別の Claude がレビュー
- **テスト先行パターン** — Claude A がテスト、Claude B が実装（構造的に TDD を強制）
- **バッチ処理** — `claude -p` でループ実行、`--allowedTools` でスコープ制限

**チーム導入のステップ**:
1. 検証の仕組みから（Hooks で Lint + テスト）
2. 設定を標準化（CLAUDE.md + Skills + Hooks を Git / Plugin で共有）
3. 自動化で拡張（GitHub Actions で CI/CD 統合）

**よくあるアンチパターン**:
| アンチパターン | 対策 |
|---|---|
| キッチンシンクセッション | 1 タスク 1 セッション。`/clear` で区切る |
| 同じ修正を繰り返す | 2 回で `/clear` + より良いプロンプトで再開 |
| 巨大な CLAUDE.md（500 行超） | 50–100 行 / 詳細はポインタ |
| 毎回手動で許可 | Auto モード + Hooks で自動化 |

## 10-6. コンテキスト 200K の内訳（スライド55–57）

### エージェントが LLM に送る 3 要素（スライド55）

```
1 回の API リクエスト = system（指示）+ tools（能力）+ messages（会話）
```

| 要素 | 内容 |
|---|---|
| **system** | 安全性ルール / ツール使用ガイダンス / 日付・git branch 等 |
| **tools** | Read / Write / Edit / Bash / Grep / WebFetch / Agent / MCP 等の定義 |
| **messages** | CLAUDE.md / ユーザー指示 / assistant 応答 / tool_result / Skill 本文 |

### 各設定ファイルの注入先（スライド56）

| 設定 | 注入先 | タイミング | 特性 |
|---|---|---|---|
| System Prompt | `system` フィールド | 常時（静的） | 絶対的、変更不可 |
| **CLAUDE.md** | messages 内（system-reminder タグ） | **毎ターン再注入** | キャッシュ境界の外 |
| Skill 本文 | messages 内（`tool_result`） | AI が呼出した時 | オンデマンド |
| Agent 定義 | サブエージェントの system + messages | 生成時に一度 | 独立コンテキスト |
| Hooks 出力 | messages 内（`tool_result`） | ツール実行前後 | 自動フィードバック |

### 200K の内訳（典型例）（スライド57）

```
System Prompt   ~12K   ┐
ツール定義      ~8K    │ 固定コスト ~25K（うち ~20K はキャッシュヒット）
CLAUDE.md       ~3K    │
MCP             ~3K    ┘
                       ──── キャッシュ境界 ────
会話履歴 + ツール結果（作業スペース） ~170K
```

**注意点**:
- **MCP は要注意** — 多数接続するとツール定義が膨らみ、200K → 実質 70K まで縮む可能性
- **会話履歴が主戦場** — ファイル読込・コマンド出力が急速に消費。70% で `/compact` 推奨
- **Skills は省エネ** — 一覧（description）は ~1K、本文は呼出し時のみ

> WS で学んだことがここに集約：
> CLAUDE.md を短く → 固定コスト削減 / Skills で段階的読込 / Agents でコンテキスト分離 / Hooks はコンテキスト外（ゼロコスト）
