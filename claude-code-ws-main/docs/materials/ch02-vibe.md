## 2-1. Vibe Coding とは？（スライド11）

> Andrej Karpathy が提唱（2025）
> **「コードを見ない。結果だけ見る。AI に任せてノリで作る。」**

仕様書もテストも書かず、自然言語の指示だけでアプリを完成させるスタイル。

### Vibe Coding の流れ

```
「〇〇作って」          AI が即興で実装    結果を見て追加指示
一言で指示      →     コード生成＋実行 →  「色変えて」「機能追加」
                                           ↓
                                         繰り返し（対話しながら育てる）
```

### 強みと注意点

| 強み | 注意点 |
|---|---|
| とにかく速い（数分で動くものが出る） | 品質が運次第（テストがない） |
| 非エンジニアでも使える | 大規模になると破綻しやすい |
| アイデア検証・PoC に最適 | 他人が引き継げない |
| プログラミング知識が不要 | 同じ指示で同じ結果にならない |

## 2-2. Vibe vs SDD 特性比較（スライド12）

| 特性 | Vibe | SDD |
|---|---|---|
| 初動の速さ | **高** | 低 |
| 品質の安定性 | 低 | **高** |
| 保守性 | 低 | **高** |
| 要件の正確さ | 低 | **高** |
| チーム再現性 | 低 | **高** |

### 使い分けが鍵

- **Vibe 向き**: PoC・スパイク、プロトタイプ、個人プロジェクト
- **SDD 向き**: 本番コード、チーム開発、長期運用

→ 今日のゴールは **使い分けができるようになること**。

## 2-3. ライブデモ（講師、10分）

### お題

「チームの日報アプリ」を Next.js で作る。

### 講師が打つ 3 段階のプロンプト

```
[0:00] 最初の一言
「Next.js で日報アプリを作って。
 名前と今日やったことを入力して、
 一覧表示できるようにして」
      ↓ 動くところまで見せる

[3:00] 追加指示を重ねる
「見た目をもっときれいにして」
「日付で絞り込めるようにして」
「カテゴリ分けを追加して」
      ↓ 機能が育っていくところを見せる

[7:00] 方向転換・大きな変更
「グラフで投稿数の推移を見せて」
「ダークモード対応して」
      ↓ ここで「破綻」や「既存機能が壊れる」が出る
```

### デモ中のトーク（講師向けガイド）

- コードは **開かない**。結果画面だけ見せる
- 「今 AI が何をしているか」は言わない（Vibe の哲学どおり）
- 壊れた挙動が出たら **そのまま見せる**（隠さない）

## 2-5. 限界診断の座談（5分）

### 観点（ホワイトボードに書き出す）

- 速さはどうだった？
- 品質は？コードは読める？
- 次に同じものを 10 人で作ったら、同じ結果になる？
- 2週間後の自分がこのコードを引き継げる？

### 期待する発言（= 次章への伏線）

- 「言い直すたびに前の機能が壊れる」 → 仕様書が欲しい
- 「同じ指示で結果が変わる」 → ガードレールが欲しい
- 「コードが読めないから直せない」 → CLAUDE.md で制約したい

> **ここで出た困り事が、そのまま体験② SDD で解消すべき課題になります。**

---

## 2-6. この章のまとめ

- Vibe は **PoC・スパイクには最強**
- 本番コード・チーム開発・長期運用には **ガードレールが必要**
- そのガードレールが **CLAUDE.md と仕様書（＝ SDD）**
