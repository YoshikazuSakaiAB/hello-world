## 5-1. SDD の回し方（スライド23）

### ウォーターフォール × SDD vs アジャイル × SDD

```
ウォーターフォール × SDD               アジャイル × SDD
---------------------               ---------------------
全仕様を先に確定                    Sprint 1: 仕様 → 実装 → 検証 ↓ FB
    ↓                              Sprint 2: 仕様 → 実装 → 検証 ↓ FB
全タスクを計画                      Sprint N: 仕様 → 実装 → 検証
    ↓
全実装
    ↓                              反復 / 小さなバッチ / 学習しながら進化
全テスト
    ↓
リリース

一方向 / 大きなバッチ / 手戻りコスト大
```

> どちらが優れているではなく、**プロジェクト特性で選ぶ**。
> Agentic Coding × SDD はどちらのプロセスにも適用可能。AI が仕様を書く速度がボトルネックを解消する。

今回のハンズオンは **アジャイル型**（1 受入条件ずつ仕様→実装→検証）で進めます。

---

## 5-2. ハンズオンの 4 ステップ（スライド24）

```
1. 配布済み仕様書を読む            → specs/daily-report.md の受入条件 6 件を把握
2. CLAUDE.md を確認                → 規約 +「テスト失敗→コード修正」を確認 / 必要なら追記
3. 1 タスクずつ実装                → 「受入条件①だけ実装して。テストも」
4. 振り返りメモ                    → Vibe との違いを速度・品質・コントロールで比較
```

> **v3 での変更**: 時間的余裕を確保するため、参加者に仕様書を書かせる工程はスキップし、**配布済み仕様書**（`exercise-2-sdd/specs/daily-report.md`）を読むところからスタートする。

## 5-3. Step 1: 仕様書を読む（5分）

### 配布済み仕様書

`exercise-2-sdd/specs/daily-report.md` に既に仕様が書かれている。参加者はエディタで開き、特に **受入条件** に目を通す。

### 仕様書の構成

- **概要 / ユーザーストーリー**: 何を作るのか
- **画面一覧**: 投稿画面・一覧画面の入力項目とバリデーション
- **受入条件**（6 件）: Step 3 で実装の単位になる
- **非機能 / 技術制約**: localStorage 永続化、ダークモードは体験③ で追加など

### 講師のフォローポイント

- **受入条件は 6 件あるが、25 分で全件は実装できない**。3 件回せれば SDD のサイクルを体感できる旨を伝える
- 「ダークモード」「投稿数グラフ」は **体験③ / 自宅課題で追加する予定** であることを明示

---

## 5-4. Step 2: CLAUDE.md を確認（5分）

### テンプレートを使う

演習ディレクトリに `CLAUDE.md` が用意されています（React + TypeScript + Vitest 前提）。

### 確認・追記すべき項目

| 項目 | 推奨内容 |
|---|---|
| 技術スタック | React / TypeScript / Vitest |
| テストコマンド | `npm test -- --run` |
| 禁止事項 | 「テスト書き換え禁止」「仕様書にない機能は実装しない」 |
| ディレクトリ構造 | `src/` + `__tests__/` |

### 体験① で困った点を活かす

第2章（体験①）で感じた困り事があれば、**禁止事項** や **コーディング規約** に追加してください。例：

- 「関数1つにつき行数は 50 行以内」
- 「any 型は禁止」
- 「コンポーネントのファイル名と default export 名を一致させる」

## 5-5. Step 3: 受入条件ごとに実装（25分）

### プロンプト例

```
specs/daily-report.md の受入条件を 1 つずつ順番に実装してください。
各実装後にテストを追加し、Vitest で検証してから次に進んでください。
最初の受入条件 #1 から始めてください。
```

### 進め方

```
受入条件 #1 → AI 実装 → テスト → Green ✅
              ↓
受入条件 #2 → AI 実装 → テスト → Green ✅
              ↓
受入条件 #3 → AI 実装 → テスト → Red → AI 修正 → Green ✅
```

### 講師のフォローポイント

- **テストが Red だった時の挙動** を観察させる（AI が自発的に修正しようとするか）
- **「仕様書にない機能」を AI が追加してきたら**、それは CLAUDE.md の禁止事項が効いていない証拠
- **25分でも全受入条件を終わらせる必要はない**。3 件回せれば十分。**仕組みが回る感覚** を持ち帰らせる

---

## 5-6. Step 4: 振り返りメモ（5分）

### 観点

- **速度**: Vibe と比べてどうだった？
- **品質**: AI の出力は仕様通り？
- **コントロール**: 「やめさせたいこと」は CLAUDE.md で止まった？
- **AI がルールを守らなかった場面** はあった？（= 第3章で予告した「70%の確率」の実感）

### 自宅課題への接続（[`homework.md`](./homework.md) 参照）

- v3 では自宅課題を **「この日報アプリを題材に、5 工程（要件定義 → 仕様書作成 → 設計 → 開発 → 確認）の AI ハーネス構成を Markdown 1 枚で構想する」** 課題に焦点化（**目安 30〜40 分 / 提出不要**）
- 完成例（Mermaid）を提示し、受講生は **それを参考に自分なりのワークフローを組む**（図の形式は自由）
- 5 工程それぞれに Skill / Sub-agent / MCP / CLAUDE.md / 既存ツールを割り当て（Hook は Day2 で扱うため任意 — 知っている人は挑戦可）
- **③ 設計の開発ルール** に TDD 制約（テスト先行 + 仕様適合チェック）を規約化（Day2 体験③④の前提）
- **Day2 当日は冒頭で 3–4 人ずつ 5 分発表 → 講師が 1 案を選び、その構成案を体験③で全員でハーネス化** する流れ。体験② で見えた「AI がルールを守らない場面」が、選ばれた受講生の設計でどう止まるかを観察できる構造にしている
