## 3-1. 仕様駆動開発（SDD）とは？（スライド15）

### 核心

> **コードを書く前に「何を作るか」を決める。**
> 仕様書（Markdown）でゴールを定義 → AI がその通りに実装 → 仕様と照合して検証。
>
> Vibe Coding の「行き当たりばったり」を、仕様というガードレールで制御する。

### Vibe Coding → SDD の流れの変化

```
Vibe Coding                         SDD（仕様駆動）
-------------                       -----------------
「〇〇作って」                      仕様書を書く（受入条件・機能一覧）
     ↓                                   ↓
AI が即興で実装                     CLAUDE.md にルールを定義
     ↓                                   ↓
結果を見て修正を繰り返す           AI が仕様通りに実装+テスト
```

### SDD にすると何が変わるか

| 観点 | 効果 |
|---|---|
| **再現性** | 同じ仕様 → 同じ品質のコード。チームの誰がやっても結果が揃う |
| **検証可能性** | 「仕様通りにできたか？」で合否が判定できる。テスト = 仕様 |
| **引き継ぎ** | 仕様書が残るので、他の人（AI も人も）が続きを開発できる |

## 3-2. CLAUDE.md — プロジェクトの「長期記憶」（スライド16）

### 書くべき内容（4 項目）

| 項目 | 例 |
|---|---|
| 技術スタック | React / TypeScript / Jest |
| コーディング規約 | 命名規則・構造 |
| テスト実行コマンド | `npm test` / `npm run lint` |
| 禁止事項 | 「テスト書き換え禁止」等 |

### 3 つのスコープ

```
~/.claude/CLAUDE.md       全プロジェクト共通（グローバル）
./CLAUDE.md               プロジェクト固有（Git で共有）
./src/CLAUDE.md           モジュール別の規約（最も狭い）
```

> **スコープが狭いほど優先度が高い。**

### コンテキストウィンドウを意識した設計（3原則）

> コンテキストウィンドウ = AI が一度に読める情報量の上限（典型 200K トークン）

| 原則 | 実践 |
|---|---|
| **短く保つ** | CLAUDE.md 本体はルールの要約だけ。長い説明文は別ファイルに分離 |
| **リンクで参照** | 「詳細は `docs/coding-rules.md` を読め」と書けば必要時だけ読み込まれる |
| **階層で分割** | 共通ルールは root、モジュール固有はサブディレクトリの CLAUDE.md に |

## 3-3. 流出コードから学ぶ CLAUDE.md 設計術（スライド43）

Anthropic 自身の Claude Code 内部の `MEMORY.md` が流出してわかった設計原則：

> - **データではなくポインタ** — 場所だけ保存し、読みに行く
> - **1行150文字以下**
> - **自分の記憶を「ヒント」として扱う** — 事実ではない、検証が必要

これを CLAUDE.md に応用します。

### 応用①：ポインタ型 CLAUDE.md

```
❌ 悪い例（長い規約を直接書く）
------------------------------
# API 規約
- 全エンドポイントは /api/v1/ 配下
- 認証は Bearer Token で...（200行続く）


✅ 良い例（ポインタで参照）
------------------------------
# API 規約
詳細は docs/api-rules.md を参照
```

→ **必要な時だけ読み込まれ、コンテキストを節約**。

### 応用②：懐疑的メモリ

CLAUDE.md の末尾にこう書く：

> この文書の情報は古い可能性がある。
> 実装前に必ず現在のコードと照合し、
> 矛盾があればコードを正として CLAUDE.md を更新すること。

→ AI が盲目的に CLAUDE.md に従う事故を防ぐ。

### 応用③：autoDream（Stop Hook で CLAUDE.md を自動更新）

Day2 第7章 Hooks で詳しく扱いますが、Stop Hook（Claude が応答完了時）で：

```
「今日学んだことを CLAUDE.md の末尾に追記して」
```

を自動実行する。次回セッションで反映される「自己学習ループ」の最小構成。

## 3-4. 指示の優先順位（スライド46）

複数の場所に書かれた指示が矛盾した場合、どちらが勝つか？ 2 つの軸があります。

### 軸①：強制力（上書き不可）

```
System Prompt（内蔵）        ← Anthropic がハードコード。変更不可
  ↓
Managed Policy              ← Enterprise 管理者が設定。組織制約
  ↓
（以下は LLM が従わない可能性あり）
```

### 軸②：CLAUDE.md 同士はスコープが狭い方が優先

```
広い ────────────────────────────→ 狭い
~/.claude/CLAUDE.md    ./CLAUDE.md    ./src/CLAUDE.md
（グローバル）        （プロジェクト）（サブディレクトリ）

優先度低 ──────────────────────────→ 優先度高
```

### その他の指示ソースと読込タイミング

| ソース | 読込タイミング | 特性 |
|---|---|---|
| Agent 定義（.md） | サブエージェント生成時 | そのエージェントのコンテキストのみ |
| Skill（SKILL.md） | AI が必要と判断 or ユーザーが `/invoke` | 読み込まれた時だけ会話に注入 |
| Rules（`.claude/rules/`） | セッション開始時（パス指定時はファイル操作時） | CLAUDE.md 同レベル、ファイル分割 |
| ユーザーのプロンプト | 毎ターン | 最も即時的・一度きり |

### 設計のコツ

> - **CLAUDE.md は「常に効く」**
> - **Skills は「必要な時だけ効く」**
> - **Hooks は「確実に効く」**
>
> 矛盾を避けるために、**同じルールを複数の場所に書かない**。1箇所で管理し、他はポインタで参照。

## 3-5. この章のまとめ

- **SDD = 仕様で AI をガイドする**。再現性・検証可能性・引き継ぎが手に入る
- **CLAUDE.md は短く、ポインタで参照、階層で分割**
- **指示の優先順位**：System Prompt > Managed Policy >（LLM 判断）。CLAUDE.md はスコープが狭いほど優先
- CLAUDE.md は「約 70% の確率で守られる」。100% 必要なルールは **Hooks で強制**（Day2 第7章）
