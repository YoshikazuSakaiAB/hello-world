## 11-1. 文書の役割の変化

| 観点 | 従来の開発 | AI 駆動開発 |
|---|---|---|
| 文書の役割 | 工程の「成果物」 | AI への「**入力ソース**」または「**出力スキーマ**」 |
| 目的 | 品質保証・監査証跡・合意形成 | AI インプット品質の担保 / 生成物の構造・品質定義 |
| 誰が作るか | 担当者が作成し責任者が承認 | AI が自動生成、担当者はレビュー・承認に集中 |
| 作り方 | 人が作成（テンプレで効率化） | コンテキストから AI が生成 → 人が承認 |
| 整合性確認 | 人の目 | AI が依存関係を追跡し矛盾を自動検出 |

> **テンプレートは「人が埋めるフォーマット」から「AI の出力スキーマ（構造・必須項目・品質基準の型定義）」へ。**

---

## 11-2. 3 層の位置づけ

### 層の全体像（上流 → 下流）

```
┌──────────────────────────────────────────────────┐
│  Layer 3 — コンテキストリポ構造ルール            │
│  （インタビュー / ペルソナ / ジャーニー /        │
│   要件 / 調査をテキストで構造化・Git 管理）      │
│  「AI の生成品質はインプット質に直結」← 最重要   │
└──────────────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────────────┐
│  Layer 2 — AI 出力スキーマ定義                   │
│  （StRS / SRS / アーキ図 / テスト / DB /         │
│   OpenAPI の各文書を「AI への出力契約」として    │
│   型定義）                                        │
└──────────────────────────────────────────────────┘
                  ↓
┌──────────────────────────────────────────────────┐
│  Layer 1 — 組織の開発規約                        │
│  （CLAUDE.md / ESLint / CI-CD / ADR /            │
│   レトロスペクティブ の雛形。                    │
│   一度整備すれば全プロジェクトで再利用）         │
└──────────────────────────────────────────────────┘
```

### 各層の配置先

| Layer | 配置先 |
|---|---|
| Layer 1 | 標準テンプレートリポ / プロダクトリポ |
| Layer 2 | Spec-Kit / AIDLC 設定 |
| Layer 3 | Context Repository |

### Layer 3 が最重要な理由

- AI の出力品質は **入力コンテキストの質に直結** する
- Vibe → SDD → Agentic と進化しても、結局 **「何を作りたいか」の解像度** が全てを左右する
- 企業の競争優位の源泉は、**コード量** ではなく **コンテキストの蓄積量**

---

## 11-3. ワークフロー

```
[1] コンテキストリポジトリ          ← Layer 3 の構造ルール
    (インタビュー / ペルソナ / 調査)
           ↓
[2] 仕様駆動開発ツール              ← Layer 2 の出力スキーマ
    (Constitution / Specify / Plan / Tasks)
           ↓
[3] 自動生成ドキュメント
    (StRS / SRS / 受入テスト / アーキ図 / DBスキーマ)
           ↓
[4] 人間のレビュー・承認
    (品質チェック / ビジネス判断 / 仕様確定)
           ↓
[5] プロダクトリポジトリ            ← Layer 1 の開発規約
    (実装 / テスト / CI/CD / リリース)
```

### 体験①②③④との対応

| 体験 | 主に触った層 |
|---|---|
| 体験①（Vibe） | 層の外側（ガードレールなし） |
| 体験②（SDD） | Layer 2（spec-template = 出力スキーマの片鱗） |
| 体験③（Agentic） | Layer 1（CLAUDE.md + Hooks + Agents = 組織の開発規約の具体） |
| 体験④（Plugin 化） | **Layer 1 を運ぶ手段** |

---

## 11-4. 導入ロードマップ

| Phase | 内容 |
|---|---|
| **Phase 1 — 基盤整備** | Layer 1 の開発規約を整備・標準化。コード規約 / CI/CD / CONTRIBUTING を作成。ADR 運用を開始 |
| **Phase 2 — コンテキスト構造化** | Layer 3 の構造ルール策定。既存のインタビュー記録・ペルソナを統一フォーマットに移行 |
| **Phase 3 — AI 出力スキーマ定義** | Layer 2 の各文書スキーマを定義。Spec-Kit / AIDLC に組み込み、パイロットで検証 |
| **Phase 4 — 継続的改善** | コンテキスト → 文書の自動生成パイプライン完成。文書間整合性チェック自動化、メトリクスに基づくスキーマ改善 |

### 成功指標

- 文書作成時間 **80% 削減**
- 文書間不整合 **95% 削減**
- 新メンバーオンボーディング時間 **60% 短縮**

## 11-5. Plugin 化との接続（体験④の発展）

体験④で作った **TDD Guard Plugin** は、Layer 1 の一部を Plugin 化したものです。

```
Layer 1 の要素（例）                Plugin 化の単位
─────────────────                ──────────────────
CLAUDE.md テンプレ                → Skills として配布
ESLint 設定                       → hooks で自動実行
テスト実行コマンド                 → PostToolUse hook
TDD 強制                          → PreToolUse hook（体験④で実装）
レビュー基準                       → reviewer agent 定義
```

> **組織のハーネスを Plugin として標準化する** ＝ 3 層スタンダードの Layer 1 の運び方の 1 つ。

### 「ゼロから作らない」の原則（第12章の予告）

- 公式・コミュニティの Plugin を探す
- 自社固有のルールだけ上書きする
- 既存テンプレートをフォークして自社仕様に

## 11-6. この章のまとめ

- AI 駆動開発では **文書の役割が変わる**（成果物 → AI の入出力）
- 3 層スタンダード：**Layer 3（コンテキスト）→ Layer 2（出力スキーマ）→ Layer 1（開発規約）**
- Layer 3 が最重要：**入力品質が出力品質を決める**
- 導入は Phase 1 → 4 で段階的に
- 体験④で作った Plugin は Layer 1 を運ぶ手段
