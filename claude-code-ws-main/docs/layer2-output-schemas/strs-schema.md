# StRS（ステークホルダー要求仕様）出力スキーマ

## 目的

ステークホルダー・ユーザーの **生の要求** を構造化して記録する。
ビジネス価値と要求の源泉を保持し、後続の SRS 生成の入力とする。

## 入力ソース

- インタビュー記録（`context-repo/interviews/`）
- ペルソナ定義（`context-repo/personas/`）
- 調査結果（`context-repo/research/`）
- ビジネス要件・制約（`context-repo/requirements/`）

## 必須セクション

1. **文書情報**
   - 文書 ID（例: `STRS-001`）
   - バージョン / 更新日 / 承認者
2. **システム概要**
   - 対象システムの目的
   - スコープと非スコープ
3. **ステークホルダー一覧**
   - 役割 / 関心事 / 影響度
4. **インタビューログ参照**
   - 各要求がどのインタビュー・ペルソナに由来するかの参照
5. **要求一覧**
   - 後述の構造

## 要求の必須項目

各要求は以下を必ず持つ：

| 項目 | 内容 | 例 |
|---|---|---|
| `id` | トレーサビリティ ID | `REQ-001` |
| `title` | 要求の要約（1 行） | ユーザーは日報を提出できる |
| `source` | インタビュー / ペルソナ ID | `INT-2025-03-15-stakeholder-A` |
| `persona` | 関連ペルソナ | `persona-primary-user` |
| `priority` | MoSCoW | `Must` / `Should` / `Could` / `Won't` |
| `rationale` | なぜこの要求が必要か | 業務の可視化のため |
| `acceptance` | 受入基準（自然言語でも可） | 日報が保存され、上長が閲覧できる |
| `constraints` | 制約 | 法的・技術的・予算 |

## 品質基準

- [ ] すべての要求にトレーサビリティ ID（`REQ-NNN`）が付与されている
- [ ] すべての要求に MoSCoW 優先度が付与されている
- [ ] すべての要求に受入基準が記述されている
- [ ] `source` が `context-repo/` 内の実在ファイルを指している
- [ ] `Must` に分類された要求は全て `acceptance` を持つ

## トレーサビリティ

- **上流**: `context-repo/interviews/`, `personas/`, `research/`
- **下流**: SRS の Epic / Feature / UserStory が `REQ-NNN` を参照

## 出力例

```markdown
# STRS-001 日報管理システム

- Version: 1.0
- Updated: 2025-03-20
- Approver: @pm-tanaka

## システム概要

従業員が日々の業務内容を記録し、上長が進捗を把握するシステム。
社内業務支援ツールの一部として提供する。

スコープ: 日報の作成・閲覧・検索
非スコープ: 勤怠管理・評価

## ステークホルダー

| 役割 | 関心事 | 影響度 |
|---|---|---|
| 一般社員 | 日報作成の手間 | 高 |
| 管理職 | チームの進捗把握 | 高 |
| 情シス | セキュリティ | 中 |

## 要求一覧

### REQ-001 日報を提出できる

- **Source**: `INT-2025-03-15-stakeholder-A`
- **Persona**: `persona-primary-user`
- **Priority**: Must
- **Rationale**: 業務の可視化のため、全社員が毎日提出する必要がある
- **Acceptance**:
  - 当日分の日報を 1 件作成・保存できる
  - 提出後、上長が閲覧できる
- **Constraints**: 個人情報を含まないこと（法的制約）
```
