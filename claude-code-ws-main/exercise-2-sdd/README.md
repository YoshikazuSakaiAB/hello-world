# 体験② SDD（仕様駆動開発）— 日報アプリを仕様から作る

> **対応スライド**: 14–24
> **進行章**: Day1 第 5 章 / **40 分**
> **パラダイム**: Context Engineering — 「何を見せるか」で勝負

## 学習目標

- **配布済み仕様書** と **CLAUDE.md** で AI をガイドする側に回る感覚を掴む
- 「仕様通りに実装されたか？」で合否判定できる（＝検証可能性）を確認する
- 体験③・④で引き継ぐ「**ベースとなる日報アプリ**」を作り上げる

## お題

体験① と同じ「日報アプリ」を、**今度は Vite + React + TypeScript + Vitest** で、**配布済みの仕様書をもとに** 作ります。

> 体験① は Next.js でしたが、ここでスタックを切り替えます。以後、**体験② → ③ → ④ はこのディレクトリの成果物を引き継いで発展** させます。
>
> ハンズオンの時間を確保するため、**仕様書はこちらで用意済み**（`specs/daily-report.md`）。参加者は仕様書を読み、AI に実装を依頼することに集中します。

## Step 1: 配布済み仕様書を読む（5 min）

`specs/daily-report.md` には、日報アプリの仕様（ユーザーストーリー / 画面定義 / **受入条件 6 件** / 非機能 / 技術制約）が既に書かれています。

エディタで開き、特に **「受入条件」** に目を通してください。これが Step 3 で AI に実装させる単位になります。

> 受入条件は 6 件ありますが、Step 3 の 25 分では **全件を実装する必要はありません**。3 件でも仕組みが回れば SDD のサイクルを体感できます。

## Step 2: CLAUDE.md を確認（5 min）

このディレクトリの `CLAUDE.md` には以下が既に定義されています：

- 技術スタック（**Vite + React + TypeScript + Vitest**）
- コーディング規約（関数コンポーネント / `any` 禁止 など）
- ディレクトリ構造 / テスト命名規則
- 禁止事項（テスト書き換え / 仕様外の実装）

体験① で感じた困り事があれば、ここの「禁止事項」に 1–2 行追記してから次へ進みましょう。

| Vibe での困り事 | 禁止事項への落とし込み例 |
|---|---|
| 「同じ指示で UI が違った」 | コンポーネント配置・命名規則を固定する |
| 「`any` だらけになった」 | `any` / `@ts-ignore` 禁止（既に記載済み） |
| 「テストを勝手に書き換えた」 | テストファイルを書き換えてパスさせない（既に記載済み） |

## Step 3: Claude Code で実装（25 min）

```bash
claude
```

セッション内で次のように指示します。

```text
specs/daily-report.md の受入条件を上から 1 つずつ実装してください。
各条件を実装したら、対応する Vitest のテストを __tests__/ に追加し、
`npm test -- --run` で検証してから次の条件に進んでください。
CLAUDE.md のコーディング規約と禁止事項を厳守してください。
```

> **ポイント**: 一気に全機能を投げない。1 受入条件ずつ回すと SDD × アジャイル（スライド 23）のサイクルを体感できます。

### 観察ポイント（ch05 参照）

- テストが Red のときに AI はどう動くか？
- 仕様にない機能を勝手に追加してこないか？
- `CLAUDE.md` の禁止事項は守られているか？
- **守られなかった場面をメモする** — Day2 体験③ で **Hooks で物理的に止める** 動機になります

- **自宅課題の詳細**: [`../docs/materials/homework.md`](../docs/materials/homework.md)
